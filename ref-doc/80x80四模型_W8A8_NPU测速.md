# 80×80 packed RAW：四模型 W8A8 NPU 部署测速

日期：2026-10-08。本次不训练，只比较固定小尺寸输入下的部署推理速度。

## 1. 测试口径

- 逻辑输入、输出均为 **NCHW `[1,4,80,80]`**，对应80×80×4 packed RAW，batch=1。
- Qualcomm AI Hub / Workbench，Samsung Galaxy S24 / **SM-S921U1 / SM8650 / Hexagon V75**；QAIRT **2.50.0.260828221209**，SDK **qai-hub 0.56.0**。同设备型号，不保证同一台物理手机。
- 编译为 QNN DLC，权重/激活8bit，量化IO；日志确认 `--weights_bitwidth 8 --act_bitwidth 8`。实际模型IO为 uint8，带 scale/zero_point；不表示偏置、累加器及所有中间计算均为8bit。
- 使用平台随机校准，不评价量化精度或PSNR。每个模型独立编译、测3轮，每轮100次，合计300个原始样本。全部12个测速任务成功，profiler条目均为NPU。
- 原始 `all_inference_times` 单位为微秒，本文除1000转为毫秒。均值/P50/P95使用全部300个样本，不剔除首个较慢样本，分位数使用线性插值；平台 `estimated_inference_time` 单独保存在JSON。
- 结果是平台报告的模型推理耗时，不包含主机网络传输、图像预处理、相机流水线等完整应用耗时。逐层插桩周期不换算成正常推理毫秒。

## 5. 分辨率、计算量与 NPU 耗时为何不严格成比例

分析补充日期：2026-10-09。本节复用已有两种尺寸的实测结果，没有重新训练、修改模型或提交新的 NPU 测速。数值结论来自保存的 profile；调度、缓存和利用率的解释属于性能模型推断，当前记录不足以把总时间精确分解到每一种原因。

### 5.1 先核对“缩小了多少”以及“倍数差距是否都减少”

逻辑像素数从 `360×640=230,400` 降到 `80×80=6,400`，减少 **36倍**，不是边长减少36倍。高、宽分别缩小4.5倍、8倍，长宽比也改变了；硬件执行不仅取决于像素总数。

以下均使用三轮全部300个样本的均值。Haar大图选择**同一个DW1×1＋ReLU＋残差变体**，没有混入原始Soft或Min/Max模型。MRLFN和SplitterNet使用前次重测数据，SplitterNet两端均为clean版本；U-Net使用最初的大图记录与本次小图clean记录。不同轮次不在同一时刻，也未保证使用同一台物理手机，U-Net/MRLFN的源图清理流程也不完全相同，因此这是部署产物的跨尺寸对比，不是所有其他条件严格受控的缩放定律实验。

| 模型 | 360×640 / ms | 80×80 / ms | 实际加速倍数 | 若严格除36的预测 / ms |
|---|---:|---:|---:|---:|
| Haar 残差 CNN | 0.5982 | 0.1079 | 5.54× | 0.0166 |
| MRLFN | 0.7682 | 0.1064 | 7.22× | 0.0213 |
| SplitterNet clean | 2.5952 | 0.1730 | 15.00× | 0.0721 |
| U-Net | 2.8483 | 0.2477 | 11.50× | 0.0791 |

所有模型都加速，但只有 **5.54～15.00倍**，远小于逻辑面积的36倍。模型间的耗时比则是：

| 耗时比（前者÷后者） | 360×640 | 80×80 | 变化 |
|---|---:|---:|---|
| MRLFN / Haar 残差 CNN | 1.28× | 0.99× | 接近1，均值顺序轻微反转 |
| SplitterNet clean / Haar 残差 CNN | 4.34× | 1.60× | 缩小 |
| U-Net / Haar 残差 CNN | 4.76× | 2.30× | 缩小 |
| SplitterNet clean / MRLFN | 3.38× | 1.63× | 缩小 |
| U-Net / MRLFN | 3.71× | 2.33× | 缩小 |
| U-Net / SplitterNet clean | 1.10× | 1.43× | 反而扩大 |

因此，**多数模型对的倍数差距缩小，但不是全部**。U-Net/SplitterNet从约1.10扩大到1.43，因为SplitterNet随尺寸缩小加速约15倍，U-Net只有约11.5倍。Haar与MRLFN小图均值只差约1.4%；而小图P50又是Haar更低（0.097 vs 0.100 ms），不能据均值的轻微反转断言稳定胜负。

数据来源：[Haar大图](qaihub_hf_cnn_20261008/summary.json)、[MRLFN/SplitterNet大图](qaihub_priority1_20261008/summary.json)、[U-Net大图](qaihub_w8a8_20261007/summary.json)、[本次小图](qaihub_80x80_20261008/summary.json)。可复核的完整比值见 [resolution_scaling_analysis.json](qaihub_80x80_20261008/resolution_scaling_analysis.json)。

### 5.2 一个更合适的耗时模型：面积相关工作＋不按面积缩放的工作

理想化模型 `T=c×H×W` 隐含了所有工作随面积变化、吞吐率固定、没有额外代价等条件。实际部署可以用下面的近似模型理解：

\[
T(H,W)\approx T_{\rm graph}
+\sum_{g\in\mathcal E(H,W)}\left[L_g+
\max\left(\frac{F_g(H,W)}{P^{\rm eff}_g(H,W)},
\frac{Q_g(H,W)}{B^{\rm eff}_g(H,W)}\right)\right]
+T_{\rm sync}.
\]

这里的 `g` 是编译后的执行单元/融合组，不等于一个ONNX节点：

- `F` 是实际算术工作，`Q` 是相应存储层级的数据流量；数据流量不是简单的“峰值特征内存”。
- `P_eff`、`B_eff` 是有效计算吞吐率和有效带宽，随算子、张量形状、缓存命中和调度变化，不等于芯片宣传的峰值。
- `L_g`、图执行和同步部分并不都随像素数线性缩小。实际执行可重叠、流水化，因此这只是解释瓶颈的模型，不是可直接代入峰值TOPS得到毫秒的精确公式。

计算与访存瓶颈、缓存、启动代价共同影响深度学习算子性能的分析框架，可参考原始研究 [Time-Based Roofline for Deep Learning Performance Analysis](https://arxiv.org/abs/2009.04598)。它提供一般方法，不能直接证明本次Hexagon上每一项开销的具体数值。

把模型进一步简化为 `T_m(P)≈A_m+B_mP`：大图时面积相关的 `B_mP` 更突出；小图时不随面积同比缩小的 `A_m` 占比增加。若两个模型的 `A_m` 接近，即使大图耗时差很多，小图比值也可能接近1。**但每个模型的A都可能不同，所以并不保证所有模型差距都缩小或趋近1。**

不能用只有两个尺寸的数据拟合一个截距，就宣称测到了固定的RPC耗时或硬件启动时间。本次没有相应时间线，也不能把云端排队、上传、编译或Python调用的墙钟时间加到平台报告的推理耗时中。本文所说的固定/弱缩放代价，仅指落在该推理计时范围内的执行代价；其内部构成尚未被直接测量。

### 5.3 为什么减少36倍像素，不会减少36倍工作或耗时

**第一，内部处理尺寸不一定就是逻辑输入尺寸，尤其是当前U-Net。**

当前 [UNetSeeInDark.check_img_size](../models/ELD_models.py) 使用：

```python
mod_pad_h = 16 - h % 16
mod_pad_w = 16 - w % 16
```

它没有在最后再 `%16`，所以当边长已经整除16时仍会补16。这是当前模型的实际行为，不是本次分析新加入的修改：

| 模型 | 大图主要处理空间 | 小图主要处理空间 | 两者面积比 |
|---|---|---|---:|
| Haar/MRLFN（packed RAW域） | 360×640 | 80×80 | 36.00 |
| SplitterNet入口对齐后 | 368×640 | 80×80 | 36.80 |
| **U-Net入口补边后** | **368×656** | **96×96** | **26.19** |

已检查U-Net小图ONNX：首层卷积的 `pads=[1,1,17,17]`，输出为 `[1,32,96,96]`；因此“clean图没有独立Pad节点”不意味着没有补边计算，Pad被融合到卷积属性里了。大图原始ONNX的首层输出也已通过ORT检查为 `[1,32,368,656]`。小图的四级池化瓶颈实际为6×6，不是按80/16猜测的5×5。

U-Net在小图上96×96相对80×80多 **44%** 的空间位置，这解释了其实际卷积工作不能简单按逻辑面积除36；但不能据此声称44%的端侧耗时都能消除。其他算子、硬件调度和缓存仍参与计时。补边策略改变还可能改变边界输出，若后续要优化，应单独做保留原权重的输出核对和测速对照，不在本次分析中直接删改。各层转置卷积、边界和裁剪也会使精确Op比例偏离上表的面积比。

**第二，算子规模缩小，网络的串行步骤不会同比减少。**

首轮NPU profiler条目数如下，其余轮次也可在原始JSON中核对：

| 模型 | 大图profiler条目数 | 小图profiler条目数 |
|---|---:|---:|
| Haar 残差 CNN | 60 | 60 |
| MRLFN | 49 | 49 |
| SplitterNet clean | 492 | 491 |
| U-Net | 54 | 54 |

Haar、MRLFN、U-Net条目数不变，SplitterNet只少1项。层数、分支依赖和逐层完成的顺序没有随面积减少36倍。条目数不是独立硬件启动次数：可能有融合、别名或0周期记录，也不能用“条目数×某固定延迟”估计整网。但这些记录至少说明图并未因分辨率变小而缩成原来的1/36个步骤。

**第三，小特征图通常更难维持大图时的计算利用率。**

Haar的LL3从45×80变为10×10，精修主干从180×320变为40×40；MRLFN主干也从180×320变为40×40。可并行的空间工作减少，可能出现更少的工作块、尾块填不满、依赖等待占比上升等情况。硬件分块、对齐通常具有离散粒度，张量少一点不一定减少一个完整执行块；`P_eff`不能假定恒定。本次没有采集硬件占用率计数器，因此这是符合结构的解释，不是已测得某个模型具体的利用率百分比。

**第四，特征大小缩小，但权重规模不变，缓存与访存的变化也不线性。**

本次部署CNN参数约为Haar 8.65万、MRLFN 13.07万、SplitterNet 73.16万、U-Net 776.05万；同一模型换分辨率不会减少这些参数。更小的空间张量降低每组权重可复用的输出位置数量，可能改变计算与数据供应的平衡。但缓存命中可能又因工作集变小而改善，跨过片上存储容量边界还可能产生台阶式变化。不能把“参数字节数”直接当成每次推理必然从外存读取的字节数，也没有证据证明这四个模型在本次80×80时都完全驻留片上。

**第五，编译器按静态shape选择实现和融合，速度曲线可以有台阶。**

两种尺寸分别编译，后端可能改变分块、缓冲复用、布局转换或融合方案。即便源图或profiler条目数相同，也不保证最终内核实现和内存流量相同。反过来，删除源图中的一个Pad/Reshape，也不保证端侧少执行一项工作，因为原图可能早已在编译时折叠。需要查看实际部署产物和测量，不以ONNX节点数作为速度代理。

### 5.4 为什么计算量更低的网络，实际不一定更快

对固定形状的一层分组卷积，主要算术量约为：

\[
F_{\rm conv}=2H_oW_oC_o(C_i/G)K_hK_w.
\]

只有通道、核、组数、内部空间比例固定且忽略边界取整时，它才近似随输入面积线性变化。即使F精确缩小36倍，也还需要有效吞吐率不变，时间才可能同比缩小。

这四个网络包含不同的算子组合：

| 路径 | FLOPs/MACs之外需要关注的内容 |
|---|---|
| Haar | 小波卷积/逆变换、12通道DW、Split/Concat和多级依赖；小通道卷积不一定达到宽卷积的利用率 |
| MRLFN | 较规则的主干卷积与残差路径；算术量较高仍可能被后端更高效地执行 |
| SplitterNet | 多分支、反射Pad、Slice/Concat、归约和注意力，许多操作算术少但仍有数据访问及依赖 |
| U-Net | 较宽的卷积、大量权重、编码解码和skip拼接，以及本实现额外补边 |

例如，Concat/重排在算法统计里可能记0算术Op，但物化时需要搬运数据；若后端可用视图或融合消除拷贝，其代价又可能很低。DW卷积比全卷积少很多MAC，也未必按同倍数省时，因为通道混合、权重复用和硬件映射不同。PReLU、归约、卷积即便都记作若干标量Op，其硬件执行代价也不相等。因此 **GOp/TOPS只能在算子适配、利用率、访存和计数口径明确时给出理想参考，不能直接预测整网端侧延迟**。

特别是SplitterNet：大图时随特征面积增长的数据处理代价可能较突出，小图时这部分下降较多，所以本次加速倍数高于Haar；它仍保留大量串行分支步骤，因此80×80也没有必然快于MRLFN。U-Net/SplitterNet比值扩大，则与二者不同的内部尺寸缩放、权重规模和执行效率相容。现有数据不能唯一确定这些因素各贡献多少。

### 5.5 如何使用这些结果，以及进一步确认原因

当前可以确认的是：四模型的时间都不按逻辑面积同比缩小；多数跨模型差距收窄但存在明确反例；小图Haar/MRLFN处于接近水平；U-Net还存在实际内部补边差异。不能确认的是：固定执行代价、权重传输、缓存收益、空闲计算单元分别占了多少时间。所有任务条目均为NPU，这一现象不能直接归咎于已发生CPU回退。

若后续要将解释变成可量化结论，可安排同一物理设备上的多尺寸、同长宽比测试，例如80²、160²、320²、640²，并另设相同面积不同长宽比的对照；固定精度、权重和运行时设置，采用一致预热并交错测试模型以降低温度/频率漂移影响。结合后端可提供的内核、数据流量与硬件计数器，分别验证调度、缓存和利用率的贡献。U-Net“整除尺寸仍补16”的实现适合单独作为一个补边对照组，而不是悄悄混入现有基线。

以上是后续验证方向，本次只补充分析，未执行这些新实验。部署选型仍应按实际目标分辨率比较完整模型的延迟及效果；80×80的排名不能直接外推到360×640，也不能用更大的batch吞吐量替代batch=1的逐帧延迟。
